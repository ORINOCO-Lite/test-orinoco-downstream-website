# Operating the CON Orinoco test site

This guide covers the site-owned layer of `test-orinoco-downstream-website`.
It is for reviewing and operating this concrete full-content test site, not for maintaining the generic template or implementing the Orinoco engine.

The repository deliberately carries the complete accepted CON content baseline,
subsequent reviewed source-adapter metadata and provenance records, ten editorial
sources, 71 declared content assets, the accepted presentation snapshot, and
consumer-specific behavior tests.
There is no content-selection subset.

This repository is a distribution fixture, not a production-content approval.
Reuse is encouraged under the matrix in [`LICENSES.md`](../LICENSES.md): original software is MIT, original prose is CC BY 4.0, and factual metadata is CC0 1.0.
Media and third-party material remain subject to their item-specific licenses and notices.

## Ownership boundaries

| Path | Responsibility |
| --- | --- |
| `metadata/records/` | Every Things YAML record supplied to projection; preserve stable PIDs. |
| `.orinoco-lite/` | Implementation support behind the checked commands. |
| `custom/editorial/` | Human-authored pages and navigation content. |
| `custom/assets/` | Site-owned payloads and the digest/retrieval contract in `custom/assets/manifest.yaml`. |
| `site/config/`, `site/layouts/`, `site/static/` | CON-specific Hugo configuration and presentation overrides. |
| `site/framework/` | Accepted presentation snapshot retained by this consumer; changes require an ordinary downstream review. |
| `source-adapters/` | Optional, read-only source-ingestion evidence and tools; never a deployed runtime dependency. |
| `extensions/` | Stable site-owned customization hooks. |
| `generated/` | Ignored projection output regenerated by validation and builds. |
| `orinoco.lock` | Exact template, engine, runtime, and reusable-workflow release authority. |

The template owns a small framework facade around those paths: workflows, commands, updater and ownership tools, and generic contract documentation.
The executable ownership contract at `.orinoco-lite/template-ownership.yml` is authoritative when the prose and a path disagree.
The updater protects site-owned bytes and stops for review rather than silently reconciling them.

## Edit, validate, and preview

For a record-metadata change:

```console
pixi run validate
pixi run hugo-projection-update
pixi run projection-verify
pixi run build
pixi run serve
```

`validate` and `build` depend on `hugo-projection-update`, which recreates ignored pages, the record stream, and graph under `generated/projection/`.
Review the source metadata diff and the rendered build; do not commit or hand-edit projection output.

Editorial, presentation, and committed asset changes do not alter record metadata, but still require validation and a complete build review.
When changing `custom/assets/manifest.yaml`, preserve the declared source, size, digest, storage, and retrieval evidence and then run:

```console
pixi run assets-hydrate
pixi run assets-verify
pixi run build
```

Before merging any content or presentation change, run `pixi run test-all`.
It is intentionally broader than the fast `pixi run test` suite.

## Local and Pages URL behavior

`pixi run build` creates `build/site` with `/` as its base URL.
The output contains root-relative navigation and asset references rather than a baked loopback origin.
`pixi run serve` serves that artifact on port 8765; both `http://127.0.0.1:8765/` and `http://localhost:8765/` are valid views of the same files.

GitHub Pages is a separate build, not a relocation of `build/site`.
The Pages workflow supplies the repository's explicit public base URL to `pixi run build-pages`, so navigation and assets retain the `/test-orinoco-downstream-website/` project path.
The checked browser fixture uses that same project-path shape locally.
Do not hard-code a loopback origin, Pages hostname, or production domain into site-owned content or configuration.

## Asset storage

The 71 content assets declared in `custom/assets/manifest.yaml` have two storage policies:

- 55 payloads are committed as ordinary Git files; and
- 16 large, digest-addressed payloads are hydrated on demand from their declared read-only URLs by `pixi run assets-hydrate`.

Hydration writes to ignored Orinoco cache state, not to the tracked source tree.
`pixi run assets-verify` verifies the cached or committed bytes against their declared sizes and SHA-256 digests without silently fetching them.
Run hydration first in a cold clone or before beginning the documented [warmed-cache offline acceptance procedure](../.orinoco-lite/tests/offline/README.md).

The presentation framework, including its compiled stylesheet and images, is stored as ordinary Git files.
Building and viewing the site requires neither DataLad nor an external large-file backend.

## Browser editor review bundles

The static editor is a review handoff, not a write service:

1. Build and open the site, follow **Edit this record**, make the intended change, and choose **Save**.
2. In the download panel, select the intended records and choose **Download review bundle**.
3. Keep the downloaded JSON unchanged and use a clean checkout of the commit from which it was created.
4. Dry-run the bundle locally and inspect the reported unified diff:

   ```console
   pixi run apply-editor-bundle -- "/path/to/orinoco-review-bundle.json"
   ```

5. After reviewing that exact diff, apply it explicitly:

   ```console
   pixi run apply-editor-bundle -- "/path/to/orinoco-review-bundle.json" --write
   ```

6. Run `validate` and the normal build and test review before committing the focused YAML change.

The browser has no repository token or metadata-service credential and makes no write request.
The local command rejects stale commits or source digests, unknown or duplicate PIDs, path escapes, identity or schema-type changes, invalid RDF, and a conflicting local change to a target record.
Without `--write`, it does not modify record YAML.

The current `/edit` interface requests the Google-hosted Roboto stylesheet and font files from `fonts.googleapis.com` and `fonts.gstatic.com` when it is opened with network access.
Whether to remove, vendor, or explicitly permit that dependency remains an engineering-level privacy and archival decision in [HR-113 — external-resource and privacy posture](https://github.com/con/orinoco-lite-dev/blob/main/docs/human-review-decisions.md#hr-113--choose-the-external-resource-and-privacy-posture).

## Framework updates

Run the non-mutating check from a clean checkout:

```console
pixi run update-check
```

An actual update must name reviewed, immutable template, engine, runtime, and workflow coordinates.
Use the complete command and review procedure in [Framework updates](../docs/updating.md), or dispatch the checked **Propose Orinoco update** workflow with those exact values.

For every update pull request:

1. review `orinoco.lock`, `.copier-answers.yml`, and `pixi.lock` as one release change;
2. confirm from the workflow log that protected site-owned paths did not change;
3. review any declared semantic migration separately from framework-only changes;
4. move every `site/framework/` or other site-owned change to a separate site-owned pull request unless the update declares an explicit semantic migration that has been reviewed as such; and
5. require `pixi run test-all` before human merge.

The updater does not discover partially specified releases, resolve conflicts silently, merge its pull request, or deploy Pages from the update branch.
Deferring an update means leaving its pull request open or closing it.
Rolling back a merged framework-only update means reverting the complete update commit so its template and release coordinates move together.
